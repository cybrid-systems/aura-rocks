# aura-rocks

A RocksDB-style LSM key-value engine written in [Aura](https://github.com/cybrid-systems/aura) (Soft face). Its hot leaf functions are sunk into generated C kernels by [aura-kernel-sink](https://github.com/cybrid-systems/aura-kernel-sink). Each leaf is profiled, compiled in the background, shadow-checked against the Aura body, and swapped atomically. It is kept only if the measured speedup beats the threshold; otherwise it is rolled back.

## Architecture

```
db:put!/db:delete! ──► WAL (lib/wal.aura) ──► memtable skiplist (lib/memtable.aura)
                                                   │  memtable_bytes reached
                                                   ▼
                                    flush ──► L0 SSTable (lib/sst.aura), new WAL, MANIFEST
                                                   │  l0_trigger L0 files
                                                   ▼
                       compaction: k-way merge (lib/merge.aura) of L0+L1 ──► L1 files
db:get  : memtable ──► L0 newest-first ──► L1 (bloom filter check before any block read)
db:scan : merging iterator over memtable + every SSTable, newest wins, tombstones hidden
```

| file | what |
|---|---|
| `lib/wal.aura` | Record = `"R" len(8) adler32(10) payload`. Appends use `O_APPEND` through `kernels/rocks_io.c` (optional fdatasync); there is a pure Aura fallback with `ROCKS_PURE_IO=1`. `db:open` replays the WAL and stops at the first torn or corrupt record. |
| `lib/memtable.aura` | Skiplist on parallel growable vectors (max height 12, p=1/4). Overwrites in place; a tombstone is entry type `D`. |
| `lib/mem.aura` | Memtable reps behind one interface: skiplist (`lib/memtable.aura`), vector, and hash + skiplist. |
| `lib/obs.aura`, `lib/adapt.aura`, `lib/cache.aura` | Workload observer, structure-switching controller, and block cache (LRU/LFU/clock). |
| `lib/entry.aura` | Entry = `type(1) klen(4) vlen(6) key value`. |
| `lib/block.aura` | Data block = entries + restart offsets + count. Binary search runs in `rk-block-seek`. |
| `lib/bloom.aura` | Bloom filter (`bloom_bits` per key, k = bpk·0.69, double hashing over `rk-hash`). |
| `lib/sst.aura` | SSTable = data blocks (each followed by its checksum), index, filter, and a 68-byte footer ending in `AROCKS01`. Point get, plus an iterator with seek/next. Every block read verifies the checksum. |
| `lib/merge.aura` | Merging iterator over memtable and SSTable sources, newest first. |
| `lib/db.aura` | open/put/delete/get/scan/flush/compact/destroy, plus the MANIFEST (written to tmp, then renamed) and stats. |
| `ws/hot.aura` (generated by `tools/gen_hot.py`) | The sinkable leaves, as workspace defines: `rk-checksum` (Adler-32), `rk-hash` (FNV-style 32-bit), `rk-bloom-probe`, `rk-dec` (fixed-width decimal), `rk-block-seek` (lower bound in a block). |
| `lib/leaf.aura` | The only module that calls the leaves by name. The engine calls `leaf:*`. |
| `lib/rsink.aura`, `scripts/sink.aura` | Runs `policy:sink!` on each leaf with real engine data (a 4 KB block, a 1000-key bloom filter). |

All on-disk data is 7-bit ASCII. Aura strings are UTF-8, so a char ≥ 128 is 2 bytes on disk and in C.

## Native data plane + Aura control plane (2026-10-16)

Like aura-redis: the data path is native and Aura only steers it.

```
app ──► lib/ndb.aura ──(one c-func call per put / get / delete / batch / multiget / scan chunk)──► native/rk_native.c
                                                     memtable (skiplist | vector | hash) ─► WAL ─► flush ─► SST
                                                     L0 + sorted runs, leveled | tiered compaction, LRU/LFU/CLOCK cache
                                                     counters: native atomics; sampling rings (rkn_ctl.h)
lib/nctl.aura (control plane) ◄──(one rkn_sample_v call per window)── features + EWMA + change score
      │ rules ─► background native sims (memtable replay, cache sim) ─► ndb:set! at a rotation ─► post check ─► KEEP | ROLLBACK
      │ implementation swap: candidate .so ─► model-test gate vs lib/db.aura ─► flush + reopen in the new .so ─► post check
      └► trajectory rows (lib/adapt.aura format) ─► aura-loop
```

| file | what |
|---|---|
| `native/rk_native.c`, `rkn_util.h`, `rkn_mem.h`, `rkn_sst.h` | The engine: a stateful kernel-sink module (`AURA_NMOD`, handle registry with generations). WAL `[crc32c][len][rec]`, SST blocks + index + bloom + footer `RKNSST01` with crc32c (SSE4.2), fdatasync'd like RocksDB; MANIFEST via tmp + rename. Keys and values are NUL-free. |
| `native/rkn_ctl.h` | Control kernels: op / block-access sampling (`sample_pct`, default 5%), window features + EWMA + change score, background memtable-replay and SHARDS-style cache simulations in a native thread. |
| `lib/ndb.aura` | The binding. At most one String argument per native function (aura#4554). |
| `lib/nctl.aura` | The control plane (see docs/adaptive.md). |
| `lib/db.aura` | The pure-Aura engine: the reference oracle (tests, swap gate) and the fallback. |
| `tests/test_native.aura`, `native/ctest.sh`, `tests/test_nctl.aura` | Differential test vs `lib/db.aura` (6 configs), C model test under ASan + UBSan (a deliberately wrong build must fail), control-plane test. |

Measured (2026-10-16, medians of 3; [docs/vs-rocksdb.md](docs/vs-rocksdb.md), [docs/adaptive.md](docs/adaptive.md)):

| µs/op, N=20000 | RocksDB 9.10 db_bench | native engine (C driver) | from Aura, 1 call per op | earlier Aura engine + kernels |
|---|---:|---:|---:|---:|
| fillseq | 3.74 | 2.86 | 254 | 15,410 |
| fillrandom | 4.77 | 6.06 | 284 | 23,434 |
| readrandom | 3.26 | 1.17 | 249 | 17,429 |
| readseq (per entry) | 0.33 | 0.05 | 293 | 16,656 |
| readmissing | 0.42 | 0.19 | 605 | 17,663 |

- Engine against engine, the native data plane is in RocksDB's range (fills 0.8–1.3×, reads faster; a much smaller engine, and Debian's db_bench has assertions on).
- From an Aura program, an op costs 120–600 µs, of which the engine is ≤ 7 µs: the rest is the interpreter loop, key building and the call boundary. That is 29–109× faster than the earlier Aura engine with kernels. Batching 100 ops per call is slower from Aura (the batch is encoded and decoded in Aura).
- Control plane: `nctl` costs 1.75 s per 24,500-op phase-bench run (72 µs/op, 36 ms per window, 27 of 49 windows skipped by the native change detector), 6× less than its first version (Aura stats parsing, rules every window) and ~65× less per op than the Aura-engine controller. The price is one more window (500 ops) of reaction lag.
- Adaptive vs best static: on data-plane time adaptive won one batch (20.4 vs 31.6 µs/op) and lost the other (43.1 vs 34.9) on a box shared with compiles, so not conclusive. On wall time it still loses by 1.04× (1,170 vs 1,127 µs/op), because the controller's 72 µs/op exceeds the ~10 µs/op it can save.

## Kernel sink

`aura-kernel-sink` moves the engine's hot Aura code into C and keeps it there only when it pays. The engine has 15 hand-written C kernels in `kernels/rocks_leaves.c`, each with an Aura reference define in `ws/hot.aura` (generated by `tools/gen_hot.py`). The reference is the specification, the shadow-gate oracle, and the fallback when a kernel refuses an input.

How a kernel is installed: `policy:sink-host!` (aura-kernel-sink `lib/policy.aura` + `lib/csink.aura`) runs these steps for each one, and `lib/rsink.aura` drives it over the engine's sample data.

1. Profile the Soft define (SKIP below the floor).
2. Compile once into a content-addressed `.so`, then load it and check the ABI.
3. Install the raw c-func into the entry point's **host slot** in `lib/leaf.aura`.
4. Shadow-gate it on edge cases (ABORT and uninstall on a mismatch).
5. Run the golden check and timed score: KEEP, or uninstall (ROLLBACK).

The workspace is never mutated (no `mutate:rebind`), which avoids aura#4550 and #4547.

| kind | kernels | what one call replaces |
|---|---|---|
| fine | rk-checksum, rk-hash, rk-dec, rk-block-seek, rk-pad | one Adler-32 / hash / field / block lower bound |
| record / block | rk-entry-encode, rk-wal-record, rk-block-build, rk-bloom-build, rk-bloom-may, rk-block-get, rk-cache-sim | a WAL record, a data block, a whole filter, a point lookup in a block, a cache-policy simulation over a trace |
| whole table | rk-sst-build, rk-sst-merge, rk-scan | a flushed SST, a whole compaction (k-way merge of the input files' bytes), a whole `db:scan` |

Decisions in the last policy run:
- KEEP for 12 kernels, from rk-entry-encode at 2.2× up to rk-sst-merge at 2611×.
- ROLLBACK for rk-hash, rk-dec and rk-bloom-may (≈1×): about 100 µs of Soft work per call, while the host-slot entry costs about 60 µs over the raw c-func.

## Adaptive structures

Some of the engine's structures are chosen while it runs, from the observed workload, instead of being fixed at open time as in RocksDB:

- the memtable rep: skiplist, vector, or hash + skiplist;
- the compaction style (leveled or tiered) with its L0 trigger and max runs;
- the block cache eviction policy (LRU, LFU or clock);
- whether point reads consult the filters.

How it works:

- Each choice is a workspace define.
- `lib/adapt.aura` hot-rebinds a define (`mutate:rebind`) only after a gate:
  - memtable: a shadow replay that compares answers;
  - cache: a simulation of every policy on the recent block accesses.
- After a swap, it compares the measured wall time per op. It rolls the value back on a regression.
- It logs every decision as a JSONL trajectory, which aura-loop ingests to propose thresholds (`--adapt-ingest`, `--adapt-propose` → `ADAPT_PROPOSAL`).

Measured results, in ms/op ([docs/adaptive.md](docs/adaptive.md), 2 runs each):

| workload | best static | adaptive |
|---|---|---|
| bench_adapt total (write seq → read → scan → write random) | 26.5 (hash:tiered) | 37.0 |
| — write-seq phase | 22.4 (vector:tiered) | **17.2** |
| — scan phase | 113.9 (skiplist:leveled) | **94.6** |
| bench_cache total (hot reads → hot+scans → moved hot set → misses) | 52.6 (lru; no cache 62.7) | 61.3 |

The switches work and are correctness-gated: the model tests run every rep × style, and every benchmark ends with 0 wrong answers. Adaptive wins the phases whose shape it detects (bulk sequential writes, scans).

It does not yet win overall, for three reasons:

- the controller's gates run in Soft, which costs about 3–9 ms/op;
- a tiered → leveled switch costs a full merge;
- the EMA lags behind phase changes.

Details and the remaining gaps are in [docs/adaptive.md](docs/adaptive.md).

## Run

```sh
git clone --recursive https://github.com/cybrid-systems/aura-rocks && cd aura-rocks
# Aura fc85608c4 or newer (see STATE.txt), built with cmake; run in ghcr.io/cybrid-systems/dev:v1.0.9
export AURA_BIN=~/aura/build-rel/aura
scripts/run_tests.sh                       # unit, sstable, db (randomized vs oracle, recovery, torn WAL), leaf rebind guard
. scripts/env.sh && kernels/build_io.sh    # librocks_io.so (run_tests does this too)
REPS=2 scripts/bench_adapt_all.sh          # static memtable rep x compaction style vs adaptive
REPS=2 scripts/bench_cache_all.sh          # cache policies vs adaptive; tools/bench_table.py build/bench_*.jsonl
BENCH_N=1000 $AURA_BIN scripts/bench.aura              # pure Aura
BENCH_N=1000 BENCH_SINK=1 $AURA_BIN scripts/bench.aura # sink first, then the same workloads
$AURA_BIN scripts/sink.aura                             # policy only (SINK_ONLY, SINK_MIN_SPEEDUP, SINK_MIN_SOFT_US)
```

Using it from Aura:

```scheme
(require "hot" all:) (require "db" all:)
(hot:load!)                       ; top-level statement, see "Aura issues"
(define db (db:open "/tmp/db" #f)) ; #f = default options (memtable_bytes 65536, l0_trigger 4, ...)
(db:put! db "k1" "v1") (db:delete! db "k1") (db:get db "k2") (db:scan db "a" "z" 100)
```

## Aura issues found

- **aura#4546**: `(define x (f))` is silently left unbound when `f` runs `set-code` + `eval-current` of a source with a letrec loop. Repro: `probes/aura4546.aura`.
- **aura#4547**: if the workspace is loaded while a module is loading, later `mutate:rebind`/heal makes module code call a different global, silently or with `invalid closure`. Repro: `probes/aura4547/`.
- Workaround for both: `(hot:load!)` must run as a top-level statement of the main program. `db:open` refuses to run otherwise, and `tests/test_leaf.aura` checks that every rebind and heal reaches the right leaf.
- aura#4548 (`string-ref`/`substring` cost grew with the index even on ASCII strings; a random read on a 270 KB SSTable took more than 350 ms per get) is fixed in Aura fc85608c4. `sst:open` no longer cuts the file into per-block strings, and the WAL replay no longer cuts each record out. Repro: `probes/string_ref_cost.aura`.
- aura#4549 (`sort`/`list-sort` returned `()` for strings and truncated floats) is fixed in Aura 602c648d3. `ru:sort-idx` now uses native `list-sort` with a comparator, and the hand-written merge sort is gone. Repro: `probes/sort_nonint.aura`.
- aura#4537 (list corruption after about 100 workspace calls) reproduced on 542fb9254 and is fixed on 89cbd6c2b (the earlier pin; now fc85608c4 for aura#4549).
- **aura#4550**: after a few `mutate:rebind` + `eval-current`, a caller of a rebound define throws "eval_flat: invalid closure". This is why kernels go into host slots instead of being rebound.
- **aura#4551**: `c-func` does not check argument types. A String passed to an Int slot sends garbage; an Int passed to a String slot crashes with SIGSEGV. Entry points guard every String parameter with `string?`.
- **aura#4552**: in a workspace (`eval-current`) define, an `(error ...)` that is not in tail position is silently dropped, and a callee's error flows on as an Error value. Reference defines raise only in tail position.
- **aura#4554**: a short (SSO, ≤ 15 byte) String argument followed by another String argument reaches C as a dangling pointer (`ffi_marshal_args_pure` grows `str_bufs` without reserve). The native data plane passes at most one String per call; kernel-sink `nmod:load` refuses more. Repro in the issue.
- **aura#4553**: `c-func` passes at most 6 arguments and silently drops the rest. `rk-scan` packs start/end into one String, and kernel-sink `csink:load` refuses kernels with more than 6 C arguments.

## Known gaps

- The block cache (`block_cache_blocks`, off by default) is process-wide, counts blocks rather than bytes, and caches block strings, not parsed blocks. With the sink, no cache is faster than any policy.
- Native data plane: an op called from Aura costs 120–600 µs against ≤ 7 µs inside the engine (interpreter loop, String building and copies, c-func call); batching from Aura does not amortize it yet. The fixes are on the Aura side (call path, zero-copy Strings, aura#4548, aura#4554).
- `nctl` (native control plane) costs 72 µs/op, more than the data-plane time it saves. Adaptive vs best static is not conclusive on data-plane time and 1.04× worse on wall time (docs/adaptive.md). Reaction lag is 2–3 windows. Thresholds are hand defaults.
- The pure-Aura engine (`lib/db.aura`, now the reference oracle): its controller still loses 1.52× to the best static, its memtable replay gate runs in Soft, and its memtable / bloom check / obs bookkeeping are Soft.
- Pure Soft mode (no kernels) is 10–40% slower than before the coarse kernels.
- Running the full gated policy inside a process leaves it slower afterwards. The rk-sst-merge Soft reference alone takes about 180 s on the sample. Install a known KEEP set with `BENCH_KEEP` / `rsink:install-only!`.
- The test_adapt and test_cache gates are timing-based and can flip under heavy machine load.
- Known rocks-side failure: `tests/test_adapt.aura` "read phase: switched live to hash" and "post check rolled a swap back". The vector→hash memtable gate rejects every candidate: shadow-replay speedup 0.48–0.87 against `mem_min_speedup` 1.15. It fails the same way on an idle machine and on every Aura pin tried (the old pin, f242d3cbd, fc85608c4), and Aura `hash-ref` is not slow (about 5 µs above loop overhead, against about 124 µs for a 300-entry binary search). The cause is the hash rep cost in replay (a skiplist per bucket), not Aura. The threshold is unchanged for now.
- **aura#4595**: after a top-level named let, a closure created in a later top-level `let` resolves a let-bound name that shadows a global to the global. `tests/test_kernels.aura` names its corrupted input `corrupt` (not `bad`, a global counter) for this reason.
- No snapshots. Two levels only (L0, L1). ASCII-only keys and values. Single-threaded; compaction runs inline.
